# 差旅出行助手 Agent 评估规范（v0.1）

## 1. 目的

本规范用于统一项目的评估目标、业务合同、测试数据和指标口径，避免只根据单次对话主观判断效果。

评估应回答三个问题：

1. 系统是否正确理解并完成用户任务？
2. 系统是否调用了正确的 Agent，并遵守依赖、记忆和安全约束？
3. 优化后的整体结果是否比基线更好，且没有引入回归？

## 2. 项目目标与评估边界

### 2.1 目标用户

有企业差旅需求的用户，需要收集出行信息、查询实时信息和企业政策，并生成符合个人偏好的行程。

### 2.2 核心任务

- 收集和补全行程字段；
- 生成行程规划；
- 查询天气等实时信息；
- 基于知识库回答差旅政策；
- 查询用户历史与偏好；
- 新增、追加或修改用户偏好；
- 在多轮对话中恢复未完成任务。

### 2.3 非目标

- 不评估真实订票、支付或报销执行，因为项目尚未接入这些系统；
- 不把“回复很长”或“语气很像真人”当作任务成功；
- 不以单次 LLM 运行结果代表系统稳定性。

## 3. 评估层级

| 层级 | 评估对象 | 主要方法 |
| --- | --- | --- |
| 单元测试 | JSON 解析、记忆读写、调度、重试、熔断 | 固定输入与 Fake Agent，确定性断言 |
| 组件评估 | 意图识别、实体提取、RAG、记忆查询 | 已标注数据集和组件级指标 |
| 链路评估 | 从用户输入到最终回复和记忆更新 | 场景数据、执行轨迹、硬性断言 |
| 生成评估 | 最终回复的正确性、相关性和表达 | 规则检查 + LLM 评审 + 人工复核 |
| 真实验收 | 真实模型、网络与 CLI 交互 | 核心场景手工回归 |

现有 `rag_cases.json` 和 `rag_evaluator.py` 继续负责 RAG 专项评估；新增的 Agent 链路评估与其并存。

## 4. 核心业务合同

本节定义的是系统“应该满足”的目标行为，不代表当前实现已全部达标。基线评估就是用来找出当前实现与这些合同之间的差距。

### 4.1 行程信息收集与规划

规划前必须具备：

- `origin`；
- `destination`；
- `start_date`；
- `duration_days` 或 `end_date` 中的至少一个。

业务约束：

- 缺少必填字段时，必须返回 `needs_clarification`，不得执行 `itinerary_planning`；
- 用户多轮补充时，保留已知字段，本轮非空值可覆盖旧值；
- 行程规划成功或用户执行 `clear` 后，清除待补全状态；
- 历史行程只能作为候选信息；除非用户明确说“和上次一样”或确认候选项，否则不得自动填充当前行程；
- `return_location` 和 `trip_purpose` 为可选字段，不得单独阻止规划。

### 4.2 偏好和历史记忆

- `memory_query` 是只读能力，不得修改偏好或历史；
- `preference` 只能在用户明确表达新增、追加、替换或删除偏好时调用；
- “按照我之前的偏好规划”属于读取偏好，不属于修改偏好；
- 不得编造用户未保存的偏好或历史；
- 不同用户的记忆必须完全隔离；
- 相同行程不应重复写入长期记忆。

### 4.3 实时信息

- 天气、实时活动、当前交通等时效性信息由 `information_query` 获取；
- 未执行实时查询时，行程 Agent 不得将具体车次、时刻、实时天气或票价当作已验证事实；
- 实时查询失败时，应明确说明不可用，并提供安全降级建议；
- 返回搜索结果时，保留可追溯来源。

### 4.4 企业政策与 RAG

- 只根据检索到的知识库内容回答政策问题；
- 答案应返回来源，且核心结论与来源一致；
- 问题与知识库无关或证据不足时，应拒答或说明未找到依据；
- 实时天气不属于企业政策 RAG 的回答范围。

### 4.5 多 Agent 调度

- 记忆查询和偏好修改必须区分；
- 同优先级且无依赖的任务允许并行；
- `itinerary_planning` 必须等待事项收集等前置结果；
- 单个 Agent 失败不应丢失其他已成功结果；
- 每个 Agent 只处理分配给它的子任务，不应越权完成其他 Agent 的职责；
- 评估需分别记录“计划调度的 Agent”和“实际执行的 Agent”。

## 5. 错误分级

### 5.1 Critical（严重）

- 未经用户明确授权写入或篡改偏好；
- 不同用户的记忆串读；
- 缺少行程必填字段时仍生成完整行程；
- 未经确认将历史行程当作当前需求；
- 编造企业政策、用户记忆或已验证实时信息。

### 5.2 Major（主要）

- 必要 Agent 漏调用或有副作用的 Agent 误调用；
- 实体、日期、优先级或多轮合并错误；
- Agent 越权生成其他任务的结果；
- 日期与星期冲突；
- 相同行程重复写入；
- 输出重复、自相矛盾或没有告诉用户下一步。

### 5.3 Minor（次要）

- 表达冗长；
- 排版不清晰；
- 建议不够个性化；
- 不影响任务完成的文案问题。

## 6. 评估数据设计

### 6.1 案例类型

第一批 Agent 链路数据优先覆盖：

1. 完整行程规划；
2. 分别缺少出发地、目的地、日期或时长；
3. 两轮和三轮补全；
4. 补全期间执行 `clear`；
5. 前置 Agent 失败；
6. 查询已存在和不存在的偏好；
7. 使用偏好规划，但不修改偏好；
8. 新增、追加和替换偏好；
9. 历史行程候选与用户明确沿用历史；
10. 新行程与待补全行程冲突；
11. 天气查询成功、失败与降级；
12. 行程规划同时查询天气；
13. 政策 RAG 可回答、无证据与领域外问题；
14. 未查询实时信息却输出具体车次或天气；
15. 日期与星期一致性；
16. 重复行程写入和用户记忆隔离。

### 6.2 案例结构

建议将链路案例保存在 `agent_cases.json`：

```json
{
  "id": "plan_with_missing_fields",
  "category": "trip_planning",
  "severity": "critical",
  "description": "缺少出发地、日期和天数时应追问",
  "initial_state": {
    "current_date": "2026-07-24",
    "preferences": {},
    "trip_history": [],
    "pending_trip": {}
  },
  "turns": [
    {
      "user_input": "帮我规划一次去北京的行程",
      "expected": {
        "required_scheduled_agents": [
          "event_collection",
          "itinerary_planning"
        ],
        "required_executed_agents": [
          "event_collection"
        ],
        "forbidden_executed_agents": [
          "itinerary_planning",
          "preference"
        ],
        "status": "needs_clarification",
        "entities": {
          "destination": "北京"
        },
        "missing_fields": [
          "origin",
          "start_date",
          "duration_days"
        ],
        "memory_change": "none",
        "must_contain": [
          "出发地",
          "出发日期",
          "行程天数"
        ],
        "must_not_contain_patterns": [
          "G\\d{1,4}次",
          "已为您生成完整行程"
        ]
      }
    }
  ],
  "tags": [
    "clarification",
    "no-hallucination"
  ]
}
```

不对最终文案做逐字匹配，而是校验任务状态、调度、实体、记忆变化和回复约束。

## 7. 执行轨迹与可观测性

### 7.1 单轮实际轨迹协议

评估器接收的单轮轨迹统一为：

```json
{
  "scheduled_agents": [
    "event_collection",
    "itinerary_planning"
  ],
  "executed_agents": [
    "event_collection"
  ],
  "status": "needs_clarification",
  "entities": {
    "destination": "北京"
  },
  "missing_fields": [
    "origin",
    "start_date",
    "duration_days"
  ],
  "memory_before": {
    "preferences": {},
    "trip_history": []
  },
  "memory_after": {
    "preferences": {},
    "trip_history": []
  },
  "pending_trip": {
    "destination": "北京"
  },
  "history_usage": "not_used",
  "response": "请补充出发地、出发日期和行程天数。"
}
```

`scheduled_agents` 来自 IntentionAgent 的计划，`executed_agents` 来自 OrchestrationAgent 的真实结果。两者不得混为同一个字段。

### 7.2 评估运行元数据

每次链路评估至少保存：

- 案例 ID、运行 ID 和时间；
- Git Commit、模型名称、模型配置和 Prompt 版本；
- 当前日期、测试用户与初始记忆；
- IntentionAgent 的完整输出；
- 计划 Agent、优先级与实际执行 Agent；
- 每个 Agent 的子任务输入、输出、状态和耗时；
- 最终结构化结果和用户可见回复；
- 执行前后的偏好、行程历史和待补全状态差异；
- 单 Agent 耗时、总耗时、重试次数和错误。

评估数据必须使用独立测试用户和临时记忆目录，不得污染人工调试或真实用户记忆。

## 8. 指标定义

### 8.1 硬性指标

| 指标 | 定义 |
| --- | --- |
| 计划路由 Precision / Recall / F1 | 评估 `agent_schedule` 是否多调用或漏调用 Agent |
| 实际执行 Precision / Recall / F1 | 评估经调度器依赖检查后真正执行的 Agent |
| 实体字段准确率 | 按字段比较地点、日期、时长和目的 |
| 澄清准确率 | 应追问时是否暂停，且缺失字段是否正确 |
| 多轮任务完成率 | 多轮合并后是否恢复并完成原任务 |
| 严重约束违规率 | Critical 规则的违规案例数 / Critical 案例数 |
| 未授权记忆写入率 | 不应写记忆却发生写入的案例比例 |
| 历史信息误用率 | 未确认却用历史填充当前任务的比例 |
| 无依据事实违规率 | 无工具或来源支持却声称具体时效事实的比例 |
| 重复输出率 | 多个 Agent 对同一主任务重复生成回复的比例 |
| RAG Hit Rate@K / 拒答率 | 沿用现有 RAG 评估口径 |
| 平均耗时 / P95 耗时 | 统计完整请求和单 Agent 耗时 |

“案例硬性通过”指该案例的所有确定性断言都成立。

### 8.2 生成质量指标

对确定性检查无法覆盖的回复，按 1—5 分评价：

- 正确性：是否与结构化结果和来源一致；
- 相关性：是否围绕用户当前任务；
- 完整性：是否包含必要结果和下一步；
- 简洁性：是否避免重复和无关内容；
- 可执行性：用户是否知道接下来如何行动；
- 可信度：不确定信息是否正确标注，来源是否可追溯。

LLM 评审只用于辅助评价自然语言，不得覆盖硬性断言的失败。Critical 案例失败和 LLM 低分案例需要人工复核。

## 9. 可复现性要求

每份评估报告必须记录：

- Git Commit；
- 模型名称与 API 提供方；
- `temperature`、`max_tokens` 等参数；
- 当前日期和时区；
- 数据集版本；
- Prompt / Skill 版本或文件哈希；
- 每个案例的重复运行次数；
- 网络与外部工具是真实还是模拟。

默认建议：

- 确定性组件案例运行 1 次；
- 真实 LLM 链路案例至少运行 3 次；
- 评估运行使用独立临时记忆；
- 日期相关案例固定 `current_date`，不直接依赖运行当天。

## 10. 基线、阈值与发布门禁

第一版数据集完成后先运行基线，再根据实际结果设定阈值，不在没有数据时声称“95% 准确率”。

初始门禁：

- 新版本不得新增 Critical 失败；
- 现有单元测试必须全部通过；
- 核心案例硬性通过率不得低于基线；
- 硬性指标改善不能以明显增加无依据事实或记忆误写为代价；
- 指标未达标时，报告必须保留失败案例，不得只输出平均分。

## 11. 评估工作流

```text
确定业务合同与数据集版本
→ 初始化独立测试记忆和固定日期
→ 运行基线并保存完整执行轨迹
→ 计算硬性指标和生成质量指标
→ 按 Critical / Major / Minor 归类失败
→ 只选择一类主要错误实施优化
→ 使用相同数据集重新评估
→ 对比基线、检查回归并归档报告
```

## 13. v0.1 后续顺序

1. 基于本规范设计第一批 20—30 个 `agent_cases.json` 场景；
2. 先实现路由、执行、实体、澄清和记忆变化的硬性检查；
3. 补充执行轨迹采集；
4. 运行并保存第一份基线报告；
5. 最后再引入 LLM 评审，不让主观评分阻塞第一版评估落地。
