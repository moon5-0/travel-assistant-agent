# 差旅出行助手 Itinerary Quality Evaluation 规范（v0.1 草案）

## 1. 评估目的

项目评估分成两个相互独立的阶段：

1. **System Evaluation**：判断系统有没有理解用户、调用正确 Agent、维护正确状态；
2. **Itinerary Quality Evaluation**：在行程已经成功生成的前提下，判断这份行程是否正确、合理、可执行且对用户有用。

第二阶段只评价 `ItineraryPlanningAgent` 的最终行程内容，不重复评价意图路由、澄清流程和记忆写入。这样可以区分：

- 系统流程正确，但生成的行程质量不好；
- 行程文字看起来不错，但系统实际调用或状态管理错误。

第一版优先回答一个简单问题：**用户敢不敢按照这份行程去执行？**

## 2. 评估对象与运行方式

第一版使用固定的结构化输入直接调用 `ItineraryPlanningAgent`，输入包括：

- 用户原始需求；
- 已收集的出发地、目的地、日期和时长；
- 用户明确表达的偏好；
- 必须参加的会议、预算或企业差旅约束；
- 必要时提供已经查询到的外部信息。

暂不把 `IntentionAgent` 和 `OrchestrationAgent` 放进行程质量评分链路，避免上游路由错误污染规划能力的分数。System Evaluation 继续负责验证完整业务流程。

每个场景保存以下内容，便于复现和分析：

- 固定输入和期望约束；
- Agent 原始 JSON 输出；
- 硬规则检查结果；
- LLM Judge 的各维度分数、理由和证据；
- 最终是否通过。

## 3. 什么是一份好的企业差旅行程

### 3.1 硬约束正确

行程必须忠实使用用户已经确认的信息：

- 出发地、目的地、日期和行程天数不能写错；
- 必须参加的会议或活动不能遗漏，也不能与其他安排冲突；
- 用户明确禁止的地点、交通或住宿选项不能出现；
- 明确给出的预算、酒店标准和企业政策不能被违反；
- 不得擅自把历史行程或偏好当成本次已确认事实。

硬约束优先使用代码检查，而不是交给 LLM 凭感觉判断。

### 3.2 时间与路线可执行

- 每日活动数量和节奏合理；
- 活动开始、结束和交通时间不存在明显冲突；
- 路线尽量连贯，避免没有理由的跨城或反复折返；
- 到站、入住、会议和返程之间留有合理缓冲时间；
- 对需要预约、开放时间不确定或受天气影响的项目给出确认提醒。

### 3.3 符合用户与差旅场景

- 商务差旅应优先保证会议、通勤和休息，而不是堆满景点；
- 用户提供的酒店品牌、座位、交通、预算和节奏偏好应被正确采用；
- 偏好无法满足或彼此冲突时，应说明取舍，不应静默忽略；
- 没有偏好时，不因为常识猜测而声称“这是用户喜欢的方案”。

### 3.4 事实可信且表达不确定性

- 不把未经查询的车次、票价、天气、营业时间和余票写成已确认事实；
- 可以给出建议时间段、常见交通方式和候选方案，但应提醒用户在出发前核实；
- 不编造不存在的用户记录、公司政策、预订结果或实时查询结果；
- 推荐应与输入中已有的信息相符，并能说明基本理由。

### 3.5 完整且方便使用

- 行程按天组织，日期、城市和每日主题清楚；
- 关键活动包含大致时间、地点、说明和交通建议；
- 包含必要的用餐、住宿、返程或注意事项；
- 内容不过度重复，用户能快速找到当天要做什么。

## 4. 评分方法

### 4.1 第一步：硬规则检查

每个场景在数据集中声明必须满足和禁止出现的约束，例如：

```json
{
  "required": {
    "origin": "苏州",
    "destination": "北京",
    "start_date": "2026-08-10",
    "duration_days": 3,
    "must_include": ["2026-08-11 10:00 客户会议"]
  },
  "forbidden": {
    "locations": ["上海"],
    "claims": ["已为您预订", "余票充足"]
  }
}
```

硬规则结果只有 `pass` 和 `fail`。发生致命错误时，该场景直接不通过，但仍保留质量评分用于定位问题。

### 4.2 第二步：LLM Judge 质量评分

LLM Judge 只评价难以用代码精确判断的内容，并必须为每项分数引用行程中的具体证据。采用四个维度，每项按 1～5 分评分：

| 维度 | 权重 | 主要问题 |
| --- | ---: | --- |
| 时间与路线可执行性 | 35% | 时间是否冲突、路线是否合理、节奏是否可执行 |
| 场景适配与个性化 | 30% | 是否符合商务目标、用户偏好和企业约束 |
| 完整性与可用性 | 20% | 是否覆盖每日安排、交通、用餐和关键提醒 |
| 事实可信与不确定性处理 | 15% | 是否避免编造实时事实，并正确提示核实 |

加权质量分换算为 0～100 分：

```text
质量分 = Σ（维度得分 ÷ 5 × 维度权重）
```

为减少 Judge 随意打分，评估提示词必须同时提供：原始需求、结构化约束、完整行程、评分标准和输出 JSON Schema。Judge 使用固定模型和低温度；证据与分数不一致的结果进入人工复核。

### 4.3 场景通过条件

一个场景同时满足以下条件才算通过：

1. 没有致命错误；
2. 所有硬约束通过；
3. 加权质量分不低于 70 分；
4. 四个质量维度均不低于 3 分。

70 分是第一版待校准阈值。完成首批人工复核后，再根据“人工认为可用”和“评估器判定通过”的一致性调整，不能为了提高通过率随意修改。

## 5. 致命错误

以下问题直接判定场景失败：

- 写错出发地、目的地、核心日期或行程天数；
- 遗漏必须参加的会议，或安排与会议明显冲突；
- 生成时间顺序不可能成立的关键行程；
- 明确违反用户给出的预算、禁用项或企业政策；
- 把未提供、未查询的信息描述成已经预订或已经确认；
- 生成空行程，或主体内容无法供用户执行。

普通的表达啰嗦、景点选择不够优秀、缺少次要用餐建议不属于致命错误，应在质量维度中扣分。

## 6. 对外汇报的三个指标

面试和版本报告只重点展示三个指标：

1. **Hard Constraint Pass Rate（硬约束通过率）**：全部硬约束均满足的运行次数占比；
2. **Average Itinerary Quality Score（平均行程质量分）**：通过 LLM Judge 得到的加权平均分；
3. **Fatal Error Rate（致命错误率）**：出现目的地、日期、会议冲突等严重问题的运行次数占比。

各维度分数、单项失败原因和场景通过率作为诊断数据保留，不包装成额外的核心指标。

## 7. 第一批场景设计

第一版先设计约 10 个高区分度场景，不通过简单换城市来凑数量：

| 场景类型 | 重点验证 |
| --- | --- |
| 标准三天商务出差 | 基础完整性和合理节奏 |
| 含固定客户会议 | 围绕不可移动时间安排其他活动 |
| 当天往返的紧凑行程 | 交通缓冲与不过度安排 |
| 明确酒店品牌偏好 | 是否真实采用偏好 |
| 明确预算和住宿标准 | 是否遵守企业差旅约束 |
| 禁止航班或指定交通 | 是否遵守交通限制 |
| 偏好与预算发生冲突 | 是否说明取舍并优先硬约束 |
| 已授权历史偏好的应用 | 规划 Agent 收到已授权偏好后是否正确采用 |
| 缺少实时车次信息 | 是否给候选方案并提示核实，而非编造 |
| 两地或多地连续差旅 | 城市顺序、日期和路线是否一致 |

首批场景覆盖正常规划、时间约束、偏好利用、政策遵守、事实可信和复杂路线六类能力。

## 8. 评估校准与版本记录

第一版采用以下顺序：

1. 编写约 10 个场景及其硬约束；
2. 人工先判断一批好、一般、差的行程样本；
3. 运行评估器，对比 Judge 结果与人工判断；
4. 修订含糊的评分描述和阈值，而不是修结果数据；
5. 固定 v0.1 数据集后运行当前项目基线；
6. 每次只针对低分维度优化，再用同一数据集回归。

重要版本保存人工整理的 Markdown 报告，至少记录：

- 数据集版本、模型和运行时间；
- 三个核心指标；
- 主要失败类型及代表案例；
- 本版本做过的改动；
- 优化前后对比及仍未解决的问题。

自动生成的原始 JSON 放在 `evaluation/itinerary_quality/results/`，不提交到 Git。

当前文件职责：

```text
evaluation/itinerary_quality/
├── itinerary_quality_evaluation_spec.md  # 评估边界和评分规范
├── itinerary_quality_cases.json           # 固定结构化场景与期望约束
├── hard_rule_evaluator.py                  # 确定性硬约束检查
├── run_itinerary_quality_eval.py           # 真实规划Agent运行入口
└── results/                                # 自动生成报告（Git 忽略）
```

## 9. 第一版暂不解决的内容

- 不评价实时天气、车票和酒店搜索工具本身的召回质量；
- 不验证景点、车次和价格的全部客观事实；
- 不追求用一个总分替代人工判断；
- 不在第一版引入多个 Judge 投票或复杂统计检验；
- 不把 System Evaluation 和行程质量分合并成一个项目总分。

这些内容可以在基础评估稳定后逐步补充，当前重点是建立一套可解释、能复现、能指导优化的行程质量基线。
