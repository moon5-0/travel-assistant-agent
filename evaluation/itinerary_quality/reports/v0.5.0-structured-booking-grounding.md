# Itinerary Quality Evaluation v0.5.0 结构化预订事实落地

## 1. 优化目标

v0.4.0 解决了铁路发车前缓冲问题，但行程中的车次、酒店和时间等事实仍主要依赖提示词约束。模型可能改写用户已确认的预订，也可能在未预订时编造精确车次、价格或天气。

本版本将“已确认预订”和“参考方案”分开处理，建立结构化事实链路：

1. 事项收集阶段获取去程、返程和住宿的状态与详情；
2. 调度器在多轮对话中合并待补全字段，并仅接受用户实际输入的值；
3. `booking_context` 作为规划阶段的唯一可信预订事实源；
4. 规划 Agent 输出 `booking_usage` 和 `booking_ref`，只决定如何安排，不负责复制事实；
5. 代码校验预订状态与引用是否一致，并从原始上下文确定性渲染车次、时间和酒店；
6. 对无来源的精确车次、票价、酒店价格、温度和“已为您预订”等确定性表达做高置信校验。

## 3. 评估结果

| 场景 | 硬规则结果 | 关键结果 |
|---|---:|---|
| 未预订，参考方案 | PASS | `booking_usage` 全部为 `use_reference_plan`，未输出无来源精确预订事实 |
| 已确认交通和酒店 | PASS（15/15） | G123、07:30、G456、15:30 和北京国贸全季酒店全部保留，三类 `booking_ref` 与状态一致 |

首次两案例合并运行时，已确认场景被误判为失败：模型将 `booking_usage` 放在 `itinerary` 内层，校验器只读取根层。本版本增加了层级兼容和确定性归一化：校验时合并读取两个位置，根层优先；展示前删除内层副本，只保留规范根字段。修复后定向重跑通过，同时 186 个离线回归测试全部通过。

## 4. 结论与边界

本版本可以使用的结论是：

> 项目将用户预订从自由文本提示词升级为结构化 `booking_context`，规划 Agent 只输出状态和引用，最终车次、时间和酒店由代码从原始事实确定性渲染。两个事实可靠性专项场景均通过硬规则，186 个可运行离线测试全部通过。

当前边界是：

- 专项数据集只有 2 个场景，且每个只有 1 份有效真实模型输出，不能宣称任意输入下都稳定通过；
- 本轮评估的是预订事实落地，不代表行程的完整可用性和内容丰富度。已确认场景的第 2 天内容仍过少，应由行程质量评估处理；
- 当前可信预订来源是用户确认信息，尚未接入外部车票或酒店预订 API；
- 真实模型调用仍出现过空输出和传输中断，属于后续模型调用稳定性优化范围。

下一步应先提交并固定本版本，再在独立分支处理已知的站前缓冲语义误判，然后重跑核心 10 场景评估。
