## 4. 原始结果与校准说明

原始 JSON 报告记录的是修复评估器前的结果：总体 `33/45（73.3%）`，Critical `23/30（76.7%）`。

检查失败轨迹后发现，模型使用 `destination="未明确"` 表示目的地缺失，但旧评估器把它当成了一个真实目的地，造成一次误判。v0.3.1 将以下表达统一视为“字段缺失”：

- `未明确`、`尚未明确`、`暂未明确`；
- `未确定`、`尚未确定`、`待确定`；
- `待明确`、`需要明确`、`需明确`；
- 上述词语附带解释文本的组合，例如 `未明确（需要用户补充）`。

修复后使用同一份原始执行轨迹离线重新评分，不重新调用模型。`trip_missing_destination_only` 从 `2/3` 校准为 `3/3`，因此正式归档分数为 `34/45（75.6%）`。原始 JSON 保持不变，用于保留可追溯的模型运行记录；本 Markdown 记录校准后的权威基线。

## 5. 剩余真实失败

校准后共有 11 次真实失败，主要分为五类：

1. **结构化输出解析失败（3 次）**：意图识别结果包含不可解析 JSON，系统降级到默认 `information_query`，导致行程和偏好请求路由错误。
2. **缺失日期时自动推断（2 次）**：用户没有提供出发日期，系统仍执行行程规划并写入行程历史。
3. **历史偏好查询路由不稳定（2 次）**：查询酒店偏好时，`memory_query`、`event_collection` 或 `itinerary_planning` 的选择不稳定。
4. **重复行程历史写入（3 次）**：完全相同的行程被再次追加，缺少幂等控制。
5. **重复偏好写入类型不稳定（1 次）**：重复追加 `汉庭` 时，偏好值从列表退化为字符串，虽然语义相同，但数据结构发生了不应有的变化。

## 6. 基线结论

当前系统的主要问题已经从“能否跑通”收敛为三类明确工程问题：LLM 结构化输出可靠性、缺失信息约束，以及长期记忆写入幂等性。

后续优化应逐项修复真实失败，并用相同的 v0.3.1 数据集重复运行至少 3 次。只有在相同评估条件下得到的结果，才可以与本基线直接比较。
