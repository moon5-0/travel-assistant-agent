# 差旅出行助手 RAG Evaluation 规范（v0.2 草案）

## 1. 评估目的

RAG Evaluation 用于回答三个相互独立的问题：

1. **检索是否找到真正支持答案的知识片段；**
2. **生成答案是否正确、完整，并且严格受检索证据约束；**
3. **在完整系统中，用户的政策问题是否被正确路由并得到可靠回答。**

三层结果必须分开统计。不能因为最终答案看起来正确，就掩盖检索失败；也不能因为检索命中了正确文件，就认为最终回答一定可靠。

本规范评估企业差旅政策、报销规定、预订指南、应急流程、平台使用指南和知识库内城市信息。实时天气、票价、余票、酒店库存和通用网络搜索不属于 RAG 知识库能力，应由 `query-info` 等实时查询能力处理。

## 2. 当前 RAG 链路

```text
企业差旅文档
→ 文档切分
→ BGE-small-zh-v1.5 向量化
→ Milvus Lite 存储
→ 用户问题向量化
→ 扩大候选召回
→ 相似度阈值过滤
→ 重复片段过滤
→ 返回 Top K 证据
→ LLM 基于证据生成答案
→ 返回答案、来源和检索片段
```

当前默认参数为：

| 配置 | 当前值 |
| --- | ---: |
| Embedding | `BAAI/bge-small-zh-v1.5` |
| Top K | 4 |
| 相似度阈值 | 0.50 |
| 候选倍数 | 3 |
| 近重复阈值 | 0.92 |

这些参数只能根据开发集调整，最终效果必须使用未参与调参的独立测试集验证。

## 3. 三层评估边界

### 3.1 Retrieval Evaluation：检索质量

直接向 RAG 检索器输入固定问题，不调用生成模型，重点评价：

- 是否召回包含正确答案的证据片段；
- 正确证据在结果中的排名；
- 返回片段中有多少真正相关；
- 知识库没有答案时是否不返回误导性片段；
- 检索耗时是否稳定。

检索评估不评价回答措辞，也不评价 IntentionAgent 的路由。

### 3.2 Answer Evaluation：回答质量

固定用户问题和检索结果，调用 RAG 回答链路，重点评价：

- 核心事实是否正确；
- 是否回答了用户问题所要求的全部关键点；
- 每个事实是否能被检索证据支持；
- 返回的来源是否真的支持答案；
- 无答案、证据不足或超出知识库范围时是否正确拒答。

回答评估必须同时保存用户问题、完整检索片段、最终答案和来源。Judge 不能只看最终答案。

### 3.3 End-to-End Evaluation：完整业务链路

从用户原始输入开始，验证：

```text
用户问题
→ IntentionAgent 路由到 ask-question
→ rewritten_query 保留关键限定条件
→ RAG 召回正确证据
→ 生成正确且有依据的答案
```

本层评价真实用户体验，但不替代前两层诊断。端到端失败必须能够区分为路由错误、问题改写错误、检索错误或生成错误。

## 4. 数据集设计

### 4.1 开发集与测试集隔离

旧版 21 题数据集、文件级命中评估器和本地 NumPy 复现报告已移除，不再作为新版评估的输入或结果。v0.2 将从重新设计的 **Development Set** 和独立 **Test Set** 开始，二者必须严格隔离。

数据集遵守以下规则：

- 测试问题不得参与阈值、Top K、分块方式和提示词调优；
- 测试集冻结后，以版本号管理；
- 优化过程中可以查看开发集失败原因，不能根据测试集单题结果反复改规则；
- 重要版本在固定测试集上连续运行，并完整保留失败样本；
- 禁止挑选最佳一次结果作为最终指标。

第一版独立测试集目标约 30 个高区分度问题：

| 类型 | 建议数量 | 主要验证 |
| --- | ---: | --- |
| 单一事实查询 | 8 | 金额、期限、舱位、申请时间等明确事实 |
| 多条件或多事实查询 | 6 | 一次回答多个政策点，防止只答一半 |
| 改写与同义表达 | 4 | 不依赖原文关键词仍能语义召回 |
| 相近政策区分 | 4 | 北京与杭州、国内与国际、普通与紧急场景不混淆 |
| 知识库外问题 | 4 | 天气、编程、生活问题等应拒答或转交其他能力 |
| 证据不足或条件缺失 | 4 | 不擅自补充职位、城市等级、审批级别等条件 |

数据集不能只通过替换城市名称凑数量，每个问题必须注明它验证的失败风险。

### 4.2 Gold Evidence：正确证据

每个可回答问题不仅保存正确文件，还必须标注真正支持答案的证据：

- `expected_sources`：正确父文档；
- `gold_evidence`：包含答案的原文片段或稳定的证据标识；
- `required_facts`：答案必须表达的事实；
- `forbidden_facts`：容易混淆但不得出现的事实；
- `should_answer`：知识库是否具备充分答案；
- `risk_type`：该问题主要验证的风险。

示例：

```json
{
  "id": "hotel_limit_beijing_paraphrase",
  "question": "去北京见客户，酒店一晚控制在多少以内？",
  "should_answer": true,
  "risk_type": "similar_policy_disambiguation",
  "expected_sources": ["01_travel_standards.txt"],
  "gold_evidence": [
    {
      "source": "01_travel_standards.txt",
      "contains": ["一线城市", "不超过500元/晚"]
    }
  ],
  "required_facts": ["北京适用一线城市标准", "住宿上限500元/晚"],
  "forbidden_facts": ["400元/晚", "300元/晚"]
}
```

只有召回片段同时满足证据内容要求，才算 Evidence Hit。仅命中正确文件但片段中没有答案，不算正确召回。

### 4.3 负例与边界问题

负例至少覆盖：

- 完全无关问题，如做饭、编程；
- 属于旅行但需要实时数据的问题，如明日天气、当前票价；
- 属于企业差旅，但文档没有给出答案的问题；
- 问题缺少决定答案的必要条件，例如未说明城市却询问具体住宿上限。

最后一类不能简单按“无关问题”处理。合理答案可以是指出缺少条件并请求补充，而不是编造一个统一标准。

## 5. 检索评估指标

### 5.1 Evidence Recall@K（核心指标）

在前 K 个结果中至少出现一个 Gold Evidence 的可回答问题占比：

```text
Evidence Recall@K = 前K个结果命中正确证据的问题数 ÷ 可回答问题数
```

它回答的是“系统有没有把回答所需证据交给 LLM”，是检索阶段最重要的指标。

### 5.2 MRR@K（诊断指标）

使用第一个正确证据排名的倒数衡量排序质量。正确证据排第一得 1 分，排第二得 0.5 分，前 K 个都未出现得 0 分。

MRR 用于判断是否需要重排，但不单独作为简历核心指标。

### 5.3 Evidence Precision@K（诊断指标）

返回片段中真正支持答案的比例。该指标过低意味着传给 LLM 的无关上下文过多，会增加 Token、干扰回答并提高幻觉风险。

### 5.4 Negative Rejection Rate（核心指标）

知识库无答案时，没有返回足以触发错误回答的片段，或最终明确进入无知识状态的比例。

对于“缺少必要条件”的边界问题，正确澄清也算通过。

### 5.5 Retrieval Latency（工程指标）

分别记录：

- P50 检索耗时；
- P95 检索耗时；
- 首次模型加载时间与热检索时间分开统计。

本地 NumPy 复现结果只能用于算法调试，最终报告应至少运行一次真实 Milvus Lite 链路。

## 6. 回答质量评估

### 6.1 确定性检查

优先由代码检查：

- `required_facts` 是否全部出现或被语义等价表达；
- `forbidden_facts` 是否出现；
- 返回来源是否属于检索结果；
- 无知识场景是否返回 `no_knowledge` 或合格的澄清；
- 模型调用失败是否被误记为正常回答。

金额、期限、比例、城市等级和舱位等明确事实，应优先使用结构化断言，不能只检查某一个宽泛关键词。

### 6.2 LLM Judge 评分

只有难以用代码精确判断的语义质量交给 LLM Judge。Judge 必须看到问题、Gold Facts、完整检索片段、最终答案和来源，并按四个维度各打 1～5 分：

| 维度 | 权重 | 判断重点 |
| --- | ---: | --- |
| 答案正确性 | 35% | 结论、数字、条件和适用范围是否正确 |
| 证据忠实度 | 30% | 答案中的陈述是否均可由检索证据支持 |
| 完整性与直接性 | 20% | 是否覆盖问题要求且没有回避核心问题 |
| 来源可追溯性 | 15% | 来源是否真实、相关并能支持对应结论 |

Judge 必须提供具体证据编号和扣分理由。总分由代码根据维度分计算，模型不得自行输出最终百分制成绩。

### 6.3 回答通过条件

可回答场景同时满足以下条件才算通过：

1. 检索命中至少一个 Gold Evidence；
2. 没有命中 `forbidden_facts`；
3. 所有核心 `required_facts` 正确表达；
4. 没有检索证据无法支持的关键断言；
5. LLM Judge 加权分不低于 70，且每个维度不低于 3。

不可回答场景必须拒答、澄清或转交正确能力，不能凭模型自身知识直接回答。

## 7. 端到端系统断言

端到端场景至少记录：

- IntentionAgent 是否调度 `ask_question`；
- 不应同时调用的 `information_query` 是否被误调度；
- `rewritten_query` 是否保留城市、人员级别、交通方式、时间范围等关键条件；
- RAG 实际检索问题；
- 检索到的证据与最终来源；
- 最终答案是否通过回答质量门。

知识库外的实时问题应正确路由到 `information_query`，而不是依靠 RAG 的相似度阈值兜底所有意图错误。

## 8. 第一版阈值与校准原则

以下阈值仅作为 v0.2 首轮目标，必须经过人工复核校准：

| 指标 | 初始目标 |
| --- | ---: |
| Evidence Recall@4 | ≥ 90% |
| MRR@4 | ≥ 0.80 |
| Evidence Precision@4 | ≥ 50% |
| Negative Rejection Rate | ≥ 85% |
| Answer Pass Rate | ≥ 80% |
| Unsupported Claim Rate | ≤ 5% |
| End-to-End Case Pass Rate | ≥ 80% |

阈值不能为了让当前版本通过而随意调整。首轮应人工审查全部失败样本和部分通过样本，确认评估器与人的判断一致后再冻结 v0.2 测试集与合格线。

## 9. 对外汇报指标

面试和版本报告重点保留四项，不把所有诊断数据包装成简历指标：

1. **Evidence Recall@K**：是否召回真正支持答案的证据；
2. **Answer Pass Rate**：检索和回答均正确的可回答场景占比；
3. **Grounded Answer Rate**：关键结论全部有证据支持的比例；
4. **Negative Rejection Rate**：知识库无答案时正确拒答或澄清的比例。

MRR、Precision、各维度分数、延迟和失败类型保留为诊断数据。

## 10. 版本实施顺序

v0.2 按以下顺序落地：

1. 重新设计带 Gold Evidence 的开发集；
2. 实现证据级检索评估器，计算 Evidence Recall@K、MRR@K 和 Evidence Precision@K；
3. 使用开发集校准评估器本身和必要的检索参数；
4. 冻结不参与调参的独立测试集；
5. 在真实 Milvus Lite 链路上运行未优化检索基线；
6. 实现确定性事实检查和证据约束 LLM Judge；
7. 运行回答质量基线并补充少量端到端路由场景；
8. 根据失败分布决定是否实施混合检索、重排、查询改写或分块优化。

先得到可信基线，再修改 RAG 设计。不能看到单个失败样本就立即增加规则，也不能用测试集反复调参。

## 12. 旧版评估的处理

旧版开发题、文件级命中评估器、本地稠密检索脚本和原始报告已经删除。旧报告曾得到的 `Hit Rate@4 = 100%` 等数据不再作为项目指标，也不用于证明当前 RAG 效果。

删除原因包括：

- 同一批题目同时参与调参和结果汇报；
- 命中标准主要基于父文件，而非真正答案片段；
- 没有完整评估生成答案正确性与证据忠实度；
- 没有覆盖真实 Milvus、完整 Agent 路由和多次运行稳定性。

v0.2 的第一份正式基线必须来自新版证据级评估器和独立测试集，并同时报告失败案例与适用边界。
