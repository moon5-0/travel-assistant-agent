# 差旅出行助手 RAG Retrieval Evaluation 规范（v0.2 草案）

## 1. 评估目的

RAG 的完整质量可以分为检索质量和回答质量，但 v0.2 当前只回答一个核心问题：

> **用户提出差旅知识问题后，检索系统能否找到真正支持答案的知识片段？**

本阶段不建设复杂的回答质量 LLM Judge，也不把 IntentionAgent 路由纳入 RAG 分数。原因是当前生成层主要负责将检索证据整理为自然语言，项目现阶段更需要先验证决定回答上限的检索质量。

回答质量和完整端到端评估保留为 Future Work，需要时再独立设计，不能与当前检索指标混成一个总分。

本规范评估企业差旅政策、报销规定、预订指南、应急流程、平台使用指南和知识库内城市信息。实时天气、票价、余票、酒店库存和通用网络搜索不属于 RAG 知识库能力，应由 `query-info` 等实时查询能力处理。

## 2. 当前 RAG 链路

```text
企业差旅文档
→ 文档切分
→ BGE-small-zh-v1.5 向量化
→ Milvus Lite 存储
→ 静态知识库能力边界检查
→ BGE 向量候选召回 + 内存 BM25 关键词候选召回
→ RRF（Reciprocal Rank Fusion）排名融合
→ 语义相似度安全门槛过滤
→ 重复片段过滤
→ 返回 Top K 证据
→ LLM 基于证据生成答案
→ 返回答案、来源和检索片段
```

当前默认参数为：

| 配置 | 当前值 |
| --- | ---: |
| Embedding | `BAAI/bge-small-zh-v1.5` |
| 检索模式 | 向量 + BM25 + RRF |
| Top K | 4 |
| 相似度阈值 | 0.50 |
| 向量/关键词候选数 | 20 / 20 |
| RRF K | 60 |
| 混合召回语义下限 | 0.43 |
| 近重复阈值 | 0.92 |

这些参数只能根据开发集调整，最终效果必须使用未参与调参的独立测试集验证。

## 3. 当前评估边界

### 3.1 当前实现：Retrieval Evaluation

直接向 RAG 检索器输入固定问题，不调用生成模型，重点评价：

- 是否召回包含正确答案的证据片段；
- 正确证据在结果中的排名；
- 返回片段中有多少真正相关；
- 知识库没有答案时是否不返回误导性片段；
- 检索耗时是否稳定。

检索评估不评价回答措辞，也不评价 IntentionAgent 的路由。

### 3.2 当前不评分的内容

v0.2 暂不评分：

- LLM 的语言组织、措辞和完整性；
- 回答质量的多维 LLM Judge；
- IntentionAgent 是否正确路由到 `ask-question`；
- 问题改写是否保留全部限定条件；
- 完整系统端到端通过率。

当前仍保留基础安全措施：无检索结果时拒答、提示词要求严格依据证据、来源由真实检索结果生成，并通过 FakeModel 单元测试验证检索内容进入 Prompt。这些属于功能合同，不包装成回答质量分数。

## 4. 数据集设计

### 4.1 开发集与测试集隔离

旧版 21 题数据集、文件级命中评估器和本地 NumPy 复现报告已移除，不再作为新版评估的输入或结果。v0.2 将从重新设计的 **Development Set** 和独立 **Test Set** 开始，二者必须严格隔离。

数据集遵守以下规则：

- 测试问题不得参与阈值、Top K、分块方式和提示词调优；
- 测试集冻结后，以版本号管理；
- 优化过程中可以查看开发集失败原因，不能根据测试集单题结果反复改规则；
- 重要版本在固定测试集上连续运行，并完整保留失败样本；
- 禁止挑选最佳一次结果作为最终指标。

第一版独立测试集目标约 20～25 个高区分度问题：

| 类型 | 建议数量 | 主要验证 |
| --- | ---: | --- |
| 单一事实查询 | 6～8 | 金额、期限、舱位、申请时间等明确事实 |
| 多条件查询 | 4 | 一次检索是否找回多项必要证据 |
| 改写与同义表达 | 4 | 不依赖原文关键词仍能语义召回 |
| 相近政策区分 | 4 | 北京与杭州、国内与国际、普通与紧急场景不混淆 |
| 知识库外问题 | 4～5 | 天气、编程、生活问题等不应召回证据 |

数据集不能只通过替换城市名称凑数量，每个问题必须注明它验证的失败风险。

### 4.2 Gold Evidence：正确证据

每个可回答问题不仅保存正确文件，还必须标注真正支持答案的证据：

- `expected_sources`：正确父文档；
- `gold_evidence`：由 `source + chunk_index` 组成的稳定证据块标识；
- `reference_answer`：依据 Gold Evidence 编写的人工参考答案，只用于校对题目与证据，不参与检索得分；
- `should_answer`：知识库是否具备充分答案；
- `risk_type`：该问题主要验证的风险。

示例：

```json
{
  "id": "hotel_limit_beijing_paraphrase",
  "question": "去北京见客户，酒店一晚控制在多少以内？",
  "should_answer": true,
  "risk_type": "similar_policy_disambiguation",
  "reference_answer": "北京适用一线城市住宿标准，每晚不超过500元。",
  "expected_sources": ["01_travel_standards.txt"],
  "gold_evidence": [
    {
      "source": "01_travel_standards.txt",
      "chunk_index": 2
    }
  ]
}
```

只有检索结果的 `parent_doc` 与 `chunk_index` 同时匹配，才算 Evidence Hit。仅命中正确文件中的其他知识块，不算正确召回。开发集创建和知识库重新分块后需要人工复核 Gold Evidence，避免证据编号过期。

### 4.3 负例与边界问题

负例至少覆盖：

- 完全无关问题，如做饭、编程；
- 属于旅行但需要实时数据的问题，如明日天气、当前票价；
- 属于企业差旅，但文档没有提供任何相关依据的问题。

“没有说明城市却询问住宿上限”这类条件不足问题不作为检索负例，因为检索器合理地可能找回住宿标准文档，是否追问缺失条件属于后续回答质量问题。

## 5. 检索评估指标

### 5.1 Evidence Recall@K（核心指标）

在前 K 个结果中至少出现一个 Gold Evidence 的可回答问题占比：

```text
Evidence Recall@K = 前K个结果命中正确证据的问题数 ÷ 可回答问题数
```

它回答的是“系统有没有把回答所需证据交给 LLM”，是检索阶段最重要的指标。

### 5.2 MRR@K（诊断指标）

使用第一个正确证据排名的倒数衡量排序质量。正确证据排第一得 1 分，排第二得 0.5 分，前 K 个都未出现得 0 分。

MRR 用于判断是否需要重排，但不单独作为简历核心指标。

### 5.3 Evidence Precision@K（诊断指标）

返回片段中真正支持答案的比例。该指标过低意味着传给 LLM 的无关上下文过多，会增加 Token、干扰回答并提高幻觉风险。

### 5.4 Negative Rejection Rate（核心指标）

知识库无答案时，没有返回足以触发错误回答的片段，或最终明确进入无知识状态的比例。

对于“缺少必要条件”的边界问题，正确澄清也算通过。

### 5.5 Retrieval Latency（工程指标）

分别记录：

- P50 检索耗时；
- P95 检索耗时；
- 首次模型加载时间与热检索时间分开统计。

本地 NumPy 复现结果只能用于算法调试，最终报告应至少运行一次真实 Milvus Lite 链路。

## 6. Future Work：回答与端到端评估

只有当检索基线稳定、项目确实需要进一步验证回答风险时，再考虑：

- 基于明确事实断言检查金额、期限、比例和适用条件；
- 检查最终结论是否都能被检索证据支持；
- 评估无答案时的拒答或澄清质量；
- 验证 IntentionAgent 路由、问题改写、检索和回答的完整链路。

是否引入 LLM Judge 待定。若未来引入，必须同时向 Judge 提供用户问题、完整检索证据和最终答案，不能只看答案文字评分。

## 7. 第一版阈值与校准原则

以下阈值仅作为 v0.2 首轮目标，必须经过人工复核校准：

| 指标 | 初始目标 |
| --- | ---: |
| Evidence Recall@4 | ≥ 90% |
| MRR@4 | ≥ 0.80 |
| Evidence Precision@4 | ≥ 50% |
| Negative Rejection Rate | ≥ 85% |

阈值不能为了让当前版本通过而随意调整。首轮应人工审查全部失败样本和部分通过样本，确认评估器与人的判断一致后再冻结 v0.2 测试集与合格线。

## 8. 对外汇报指标

面试和版本报告重点保留两项，不把所有诊断数据包装成简历指标：

1. **Evidence Recall@K**：是否召回真正支持答案的证据；
2. **Negative Rejection Rate**：知识库无答案时是否避免错误召回。

MRR、Precision、延迟和失败类型保留为诊断数据。

## 9. 版本实施顺序

v0.2 按以下顺序落地：

1. 重新设计带 Gold Evidence 的开发集；
2. 实现证据级检索评估器，计算 Evidence Recall@K、MRR@K 和 Evidence Precision@K；
3. 使用开发集校准评估器本身和必要的检索参数；
4. 冻结不参与调参的独立测试集；
5. 在真实 Milvus Lite 链路上运行未优化检索基线；
6. 根据失败分布决定是否实施混合检索、重排、查询改写或分块优化；
7. 回答质量与端到端评估根据项目需要另行立项。

先得到可信基线，再修改 RAG 设计。不能看到单个失败样本就立即增加规则，也不能用测试集反复调参。

## 11. 旧版评估的处理

旧版开发题、文件级命中评估器、本地稠密检索脚本和原始报告已经删除。旧报告曾得到的 `Hit Rate@4 = 100%` 等数据不再作为项目指标，也不用于证明当前 RAG 效果。

删除原因包括：

- 同一批题目同时参与调参和结果汇报；
- 命中标准主要基于父文件，而非真正答案片段；
- 没有完整评估生成答案正确性与证据忠实度；
- 没有覆盖真实 Milvus、完整 Agent 路由和多次运行稳定性。

v0.2 的第一份正式基线必须来自新版证据级评估器和独立测试集，并同时报告失败案例与适用边界。
